## Booking and fares

| Date | Decision | Affects | SRS/SPMP updated |
|---|---|---|---|
| 2026-10-05 | **Booking requires a road route.** A fare is only calculated from the OpenRouteService road distance; if no road route is available the passenger cannot book (no straight-line fare bookings). | Booking, fare | No |
| 2026-10-05 | **Standard fare is fixed.** The passenger pays the fare shown at confirmation. It is calculated from the admin-managed fare settings (base fare + per-km rate per vehicle type). It is labelled "Fare", not "Estimated fare". | Booking, fare, admin fare settings | No |
| 2026-10-05 | **Fares keep centavos.** Fares are shown and stored to the centavo (e.g. ₱40.92); they are not rounded to whole pesos. | Fare, payments | No |
| 2026-10-05 | ~~**Barangay tariffs from Poblacion** (first version).~~ Replaced by the 2026-10-11 final fare model below. | Fare | No |
| 2026-10-11 | **Final fare model.** (1) A trip between Poblacion and any point inside barangay X (by the barangay's official boundary), in either direction, is charged barangay X's admin-set tariff for the vehicle type, per trip, if that tariff is active. (2) Every other trip inside Trinidad (barangay to barangay, within Poblacion, within one barangay, or a barangay without an active tariff) uses the per-km fare. (3) Out-of-area trips use the per-km fare. All rates and tariffs are set by the admin. | Fare, admin fare settings, admin tariffs | No |
| 2026-10-14 | **Barangay tariffs are separate documents.** Stored as `barangayTariffs/{barangayId}` {name, tricycle, motorcycle, active, updatedAt, updatedBy}; admin-only writes; readable by signed-in users (one document per barangay, because one combined document exceeded the Firestore rules expression limit). Barangays without a saved tariff use per-km. Barangay IDs/names exist in `firestore.rules`, `admin/src/tariffs/barangays.ts` and `src/constants/barangays.ts`; a unit test checks they are identical — change all together. | Fare, admin tariffs | No |
| 2026-10-28 | **Barangay boundaries source.** `data/trinidad-barangays.geojson`: the 20 barangays of Trinidad, Bohol, extracted from the Philippines Subnational Administrative Boundaries (adm4, version v03, valid from 2025-02-13), PSA/NAMRIA via OCHA HDX. Credit the source in the documentation and the app's About screen; check the license on the HDX dataset page. | Fare, documentation | No |
| 2026-10-28 | **Barangay lookup.** The boundaries are mapped to the tariff IDs by name in `src/constants/barangayBoundaries.ts` (generated by `scripts/buildBarangayBoundaries.mjs`; [latitude, longitude], 5 decimals): 19 barangays plus `poblacion` (PSGC 0701244015). PSA code 0701244011 does not exist in the source. `findBarangayAt()` returns the barangay containing a point, or the nearest one within the 150 m service-area edge tolerance. Checked by `npm run test:unit`. | Fare | No |
| 2026-10-28 | **Applying tariffs (implemented 2026-10-29).** New standard bookings store `fareBasis` (`per_km` or `barangay_tariff`), the pickup and destination barangay IDs, and `perKmRate` for per-km bookings. Bookings without `fareBasis` (older app versions) are still accepted and treated as per-km. Rules check that a tariff fare equals the active admin tariff; they cannot check that the pin is really in that barangay (known limit; a server-side check needs Cloud Functions/Blaze). If the tariff changes between quote and confirm, the passenger is shown the new fare and must confirm again. If tariffs fail to load or take longer than about 5 seconds, the app uses the per-km fare. Standard fares show a fare basis line under the fare, with the same wording in the app and on the admin website: "Barangay tariff · Poblacion ↔ {barangay}", "₱{rate}/km" for per-km bookings, or "Per-km fare" for older bookings without a stored rate. Out-of-area trips show no fare basis line. | Booking, fare, rules, admin | No |
| 2026-10-30 | **Barangay search is local and typo-tolerant.** Typing a pickup or destination searches the 20 Trinidad barangays in the app (no network) from 2 characters, ignoring "Brgy", "Barangay", "Trinidad" and "Bohol", with aliases (e.g. "town proper", "centro" → Poblacion) and small typos allowed. Up to 5 barangay results are shown above place results, labelled "Poblacion (Town proper) · Trinidad" or "Barangay {name} · Trinidad". | Booking, location search | No |
| 2026-10-30 | **Barangay pin points.** Choosing a barangay puts the pin on a point well inside its official boundary (computed per barangay by `scripts/buildBarangayBoundaries.mjs`), so its tariff applies. Hand-checked points in `src/constants/barangayPinPoints.ts` override the computed ones; Poblacion's pin is the town centre. Points such as barangay halls can be added there later. | Booking, location search, fare | No |
| 2026-10-30 | **Place search uses OpenRouteService biased to Trinidad.** Place results come from ORS geocode search focused on Trinidad's centre and limited to the Philippines; places inside Trinidad are listed first, each labelled with its barangay ("· {barangay}"). If ORS fails or returns nothing, the phone's geocoder is used. To protect the free ORS quota, ORS is queried only from 3 characters, after a 400 ms pause in typing, once per identical text per app session, and not at all when the text exactly matches a barangay. | Booking, location search, ORS | No |
| 2026-10-30 | **"Move the pin" hint.** After a barangay is chosen, the passenger sees "Move the pin to your exact spot in {barangay}." with a Move pin button, which reopens that field so the passenger can tap the map at the exact spot (the pin is not dragged). The hint disappears when that location changes or the passenger dismisses it. | Booking, location search | No |
| 2026-11-01 | **Standard bookings expire.** A standard booking no driver accepts expires after an admin-set number of minutes (whole minutes 1–30, default 10, stored as `fareSettings/active.booking.requestExpiryMinutes`). The app stores `expiresAt` on each new standard booking; the rules accept it only if it is in the future and at most 35 minutes after the server time (5 minutes of clock-skew grace), and a driver can accept only before `expiresAt`. Bookings created before this (no `expiresAt`) count as expired: drivers no longer see them and cannot accept them. Expiry is shown from `expiresAt`; the booking's status is never rewritten (no Cloud Functions). The passenger sees "No driver accepted your request" with Try again (one-tap rebook; a changed fare must be confirmed again) or Cancel. Older app versions that do not send `expiresAt` can no longer create standard bookings. The admin website shows such bookings as Expired and counts only unexpired ones as open requests on the Dashboard. | Booking, drivers, rules, admin settings | No |
| 2026-11-17 | **One per-km fare formula for the app and the admin website.** The per-km formula (base fare + per-km rate × road distance, rounded to the centavo) lives in `shared/fares/index.ts` (`perKmFare`). The app's fare quote (`src/utils/fareQuote.ts`) and the admin website's fare preview (`admin/src/lib/fares.ts`) both import it; there is no second copy. A unit test checks that both use the same function. Behaviour is unchanged. | Fare, admin fare settings | No |

## Drivers, contact and privacy

| Date | Decision | Affects | SRS/SPMP updated |
|---|---|---|---|
| 2026-10-05 | ~~**Passenger cannot contact the driver yet.**~~ Replaced by the 2026-10-13 contact entry below. | Booking status | No |
| 2026-10-13 | **Contact numbers are shared only between the passenger and the assigned driver while the trip is active.** During an accepted, arrived or in-progress trip the passenger sees the driver's number and the driver sees the passenger's name and number, each with a Call button. Nobody else (e.g. drivers browsing open requests) can read them, and sharing stops when the trip is completed or cancelled. | Booking status, driver trip, privacy | No |
| 2026-10-13 | **Driver vehicle type is chosen from a list, never typed.** `vehicleType` must be exactly `tricycle` or `motorcycle`; the admin sets it with a dropdown (a typed value such as "Motorcycle " hides all requests from that driver). | Drivers, admin | No |
| 2026-10-14 | **Revoking and restoring drivers.** Admins can revoke or restore a driver's verification on the Drivers page. Revoking requires a reason ~~(visible to admins only)~~ (since 2026-11-16 the driver also reads it in a message from TriGo, see that row; revokes made before then have no message, so their reason stays admin-only) and takes the driver offline; a driver revoked mid-trip can still finish that trip. The app shows "Driver access revoked. Please contact the TriGo administrator." ~~(never the reason)~~ (the reason is in the message from TriGo, 2026-11-16) together with the support contacts. A passenger cannot confirm an out-of-area driver who was revoked after accepting; the request returns to searching. | Drivers, admin, out-of-area trips | No |
| 2026-10-24 | **Vehicle identification.** Drivers have `vehicleBrand` (1–30 characters), `vehicleModel` (1–40) and `vehicleColor` (1–20), required on new driver applications. The admin can correct them at approval and edit them on the Drivers page. Passengers see "Color Brand Model · PLATE" (e.g. "Red Honda TMX 155 · ABC 1234") once a driver is assigned and on the out-of-area "Confirm Your Driver" screen. Drivers approved before this show only vehicle type and plate until the admin fills the details in. | Drivers, booking status, admin | No |
| 2026-11-01 | **Ride request alerts are local notifications (no push).** The driver app vibrates for each new unexpired request while the driver is online, available, on no trip and holding no out-of-area offer (never for requests already open when the driver became available, nor for declined ones). It also posts a local notification (`expo-notifications`, Android channel "Ride requests", high importance) when the app is in the background, but only while the app is still running: nothing arrives once the app is closed, and Android or iOS may suspend a backgrounded app within minutes. Notification permission is explained once, before the driver first goes online (Android 13+), and can be turned on later from Profile; drivers who decline still get the in-app alerts. No server sends anything (no Cloud Functions). Never both at once: on screen the phone only vibrates; in the background only the notification rings. One request gets its own notification (fare, pickup → destination, km to pickup); two or more share one summary ("3 new ride requests"). A request's notification is removed once it is taken, cancelled, expired or declined, and all of them are removed when the driver goes offline or unavailable, accepts a trip or an out-of-area request, or signs out. Tapping opens that request (standard or out-of-area), or the Requests list for a summary, after the driver account has loaded (also when the tap starts the app); taps meant for another driver account are ignored. | Drivers, notifications | No |
| 2026-11-02 | **Daily acceptance quota (decides open decision #1).** Each driver may accept at most N passengers per day; the day resets at 12:00 AM Manila time. One admin-set limit (a whole number 1–100, default 20 while none is saved) applies to every driver, each with their own count; there are no per-vehicle or per-driver limits. A standard accept counts one. An out-of-area request counts when the driver claims the booking the passenger confirmed, never at the propose, so a passenger choosing another driver costs no slot; at the limit a driver cannot accept or propose, but a claim is never blocked (the passenger already chose them). If the passenger cancels before the trip starts, the slot is given back on the same day. At the limit the driver can still finish the current trip, sees "Daily limit reached. You can accept again after 12:00 AM.", gets no new-request alerts, and is left out of the passenger's out-of-area driver search. A limit change applies at once. Stored on `drivers/{uid}` (`acceptedCount` on `acceptedDay`) and `quotaSettings/active`; enforced by the Firestore rules. | Drivers, booking, out-of-area trips, admin | No |
| 2026-11-08 | **Post-trip driver ratings without Cloud Functions.** After a completed trip the passenger sees "Trip completed" with the final fare, the driver, Rate your driver (1–5 whole stars, optional quick tags from a fixed list, optional comment up to 300 characters), Skip, and Report a problem (the existing complaint form). A trip can be rated once, by its passenger, up to 7 days after completion (server time); later from Booking Details ("Rate driver"), which shows the rating once given. Ratings cannot be edited or deleted. One rating per booking is stored at `ratings/{bookingId}`; the driver's average comes from `driverRatings/{driverId}` = `{ratingSum, ratingCount}`, which the passenger's app raises in the same commit as the rating and the rules check exactly (sum + stars, count + 1). The app and the admin website show ratingSum / ratingCount to one decimal, or "New" before the first rating; `drivers/{uid}.rating` stays admin-only and is no longer shown. The project stays on Spark; a Cloud Function could take this over if it moves to Blaze (still pending, see Pending). | Passengers, drivers, rules, admin | No |
| 2026-11-10 | **Complaints store who was reported (`reportedUserId`).** A new complaint records the other side of the booking: the driver when a passenger reports, the passenger when a driver reports. It is `null` when the booking has no driver (a passenger can report a request nobody accepted), and never the reporter. The field is required from the start (no optional phase): the rules check it against `bookings/{id}` on create and refuse it when missing or wrong, so app builds from before this change can no longer file complaints once the rules are deployed (deploy order: indexes, then the app update and the rules together). Complaints filed before 2026-11-10 have no `reportedUserId`: the admin list shows "—" and the complaint detail page works out the person from the booking. Admin "N complaints against them (as driver / as passenger)" on the complaint, driver and passenger detail pages counts by `reportedUserId` and `reporterRole`, so it only covers complaints filed from 2026-11-10. Index: complaints (`reportedUserId`, `createdAt` DESC). | Passengers, drivers, rules, admin | No |
| 2026-11-15 | **Warnings and the in-app inbox.** An admin can warn the person a complaint is about ("Warn <name>" on the complaint page: a reason of 1–500 characters the user reads, then a confirmation). A warning is `warnings/{id}` = {`userId`, `role` (the role on that trip), `complaintId`, `bookingId`, `reason`, `adminId`, `createdAt`, `status` active/withdrawn, `acknowledgedAt`}; its ID is the complaint's ID, so one complaint leads to at most one warning (warnings without a complaint are allowed by the rules; since 2026-11-16 the Drivers "⋯" menu sends them). Only complaints that store `reportedUserId` (from 2026-11-10) can lead to a warning. Admins can only withdraw a warning afterwards, never edit or delete it; the warned user reads their own and taps "I understand" once (`acknowledgedAt`, server time). Warnings are counted only: the admin decides any suspension, nothing happens automatically. Driver and passenger pages show "N warnings (N withdrawn) · N complaints" for that role and the warning history with Withdraw. In the app the passenger Notifications tab and the driver's Profile → Messages from TriGo are the same inbox (newest first, unread highlighted, withdrawn warnings hidden); the passenger Home bell shows the number of unread warnings, and driver Home shows a banner while a warning is unread. The inbox is built to take announcements later (planned separately). The unused `notifications` collection is no longer read by the app. Booking updates are not sent to the inbox. | Passengers, drivers, rules, admin | No |
| 2026-11-16 | **Admin suspension of drivers, and messages from TriGo.** On Drivers → All drivers ("⋯" menu) and on the driver page an admin can Send warning, Suspend / Lift suspension and Revoke / Restore verification; each needs a reason of 1–500 characters that the driver reads. Suspend asks for 1 day, 3 days, 7 days or until lifted and stores the latest suspension on `drivers/{uid}`: `suspendedAt` (server time), `suspendedUntil` (later than now, or null = until lifted), `suspensionReason`, `suspendedBy`, `suspensionLiftedAt`, `suspensionLiftedBy`; only admins write them. A suspension is active while set, not lifted and not past `suspendedUntil` (it ends by itself, server time). Like the commission suspension it blocks only the standard accept and the out-of-area propose: the driver can stay online, finish a current trip and claim an out-of-area booking the passenger already confirmed. The app never reads `verificationNote`; a revoke reason reaches the driver only through the message of a revoke made from now on (older revoke reasons stay admin-only). Every suspend, lift, revoke and restore also creates `adminMessages/{id}` = {`userId`, `kind` suspended / suspension_lifted / revoked / restored, `title`, `body`, `reason`, `until`, `createdBy`, `createdAt`, `readAt`} in the same commit; the driver reads it in Messages from TriGo (opening it sets `readAt` once), and unread messages count on the badge and the Home banner. Driver Home shows a red banner while suspended ("Suspended until <date>" or "until TriGo lifts it", with the reason). Because the driver fields hold only the latest suspension, the driver page shows the history from `adminMessages`. Send warning creates a warning without a complaint (`complaintId` and `bookingId` null). On account deletion messages keep their record with `reason` and `body` cleared, and `suspensionReason` is removed from the driver record. Passengers receive no messages today; the inbox shows unknown kinds safely. | Drivers, admin, rules, inbox | No |

## Commission and earnings

| Date | Decision | Affects | SRS/SPMP updated |
|---|---|---|---|
| 2026-10-13 | **Driver Home shows fares collected, not earnings.** "Fares collected" (Today / This week, since Monday 00:00) is the sum of the driver's own completed trips' `finalFare`, labelled "Before commission". ~~Commission is not shown until the commission feature exists.~~ Commission is now shown on the driver Earnings tab. | Driver Home, earnings | No |
| 2026-10-13 | **Commission policy (final).** Admin-set PERCENTAGE of the final fare on every completed trip (standard and out-of-area). The admin sets the payment period (e.g. 3 or 7 days); the period total is due at its end. The driver pays via GCash to TriGo's admin number ~~or cash at the office~~ (GCash only since 2026-10-19) and enters the reference number; the admin confirms it on the admin website. Unpaid after the due date: a warning is shown to the driver; after the admin-set grace period: suspended from accepting bookings (can still log in and see the balance) until the overdue amount is confirmed paid; the suspension lifts automatically. Permanent ban only by the admin manually. Replaces the earlier 24-hour settlement idea. | Commission, driver payments, admin, driver suspension | No |
| 2026-10-14 | **Commission amount** = final fare × percentage ÷ 100, rounded to the nearest centavo (same as fares). | Commission | No |
| 2026-10-19 | **Commission payments and earnings: TriGo does not move real money.** Drivers pay commission by GCash only (outside the app) to TriGo's GCash account and submit the amount and GCash reference number; partial payments from ₱1.00 up to the balance are allowed and pay the oldest debt first; each reference number can be used once. The admin verifies manually and confirms or rejects (with a reason). Admin cash-outs (GCash, Maya, bank transfer) happen outside the app and are only recorded in TriGo, capped at the amount collected; records cannot be edited. TriGo's GCash account (name and number) is an admin setting in System settings, shown to drivers. Trips completed before the commission feature are not charged. Automatic payments through a payment provider (e.g. PayMongo) are a future enhancement requiring a registered business and Blaze. | Commission, driver payments, admin earnings | No |

| 2026-11-16 | **All drivers table.** Drivers → All drivers is a table of 10 drivers per page ("Showing 1–10 of 24", page numbers) with search (name, plate, email, mobile) and filters: Status (online, available, on a trip, offline), Vehicle, Account (Active by default, Suspended, Revoked, All) and Commission (paid up, due, overdue, suspended for non-payment). Ratings and complaint counts are read only for the 10 rows on screen. | Admin | No |
| 2026-11-17 | **Admin website uses a data router.** The admin routes (`admin/src/routes.tsx`) run under one catch-all route of React Router's `createBrowserRouter` instead of `<BrowserRouter>`, so pages can ask before leaving with unsaved changes (`useBlocker`). On the System tab each card (Booking requests, Out-of-area trips, TriGo GCash account, Support contacts) saves on its own, and only one card can be edited at a time. | Admin settings | No |
